## `create_comment/4` accepts `:inserted_at`

Server-side callers (e.g. the media-annotation discussion flow landing in
core) can now pass a real `DateTime` in `attrs` to backdate a newly-created
comment's `inserted_at` to the timestamp of the thing it anchors, rather than
the moment the thread was lazily instantiated by the first reply.

Traced the whole path:

- `apply_backdate/2` is called *after* `Comment.changeset/3` and *before*
  `put_attribution/2` in both `insert_comment_with_attachments/3` clauses
  (with and without media) — consistent in both branches.
- `:inserted_at` is correctly absent from `Comment.changeset/3`'s `cast`
  list (`lib/phoenix_kit_comments/schemas/comment.ex:153`), so nothing a
  client submits through a cast-driven form path can reach it.
- The only call site that builds `create_comment/4`'s `attrs` from client
  input is `CommentsComponent.do_create_comment/2`
  (`lib/phoenix_kit_comments/web/comments_component.ex:345`), and its
  `base_attrs` map is hand-built from named fields (`content`, `parent_uuid`,
  `metadata`, `attribution`) — it never forwards raw `params`, so
  `:inserted_at` is unreachable from the shipped LiveView form regardless of
  the changeset guard.
- Even a host that *did* blindly forward JSON/form params would be safe: the
  guard clause pattern-matches `%DateTime{}` specifically, and neither Phoenix
  params nor decoded JSON ever produce a native `DateTime` struct — only
  Elixir code that already parsed one can trigger the backdate. The moduledoc
  warning ("server-side callers only; never pass user input here") is
  belt-and-suspenders, not the only thing standing between this and a client.
- `DateTime.truncate(dt, :second)` matches the schema's
  `timestamps(type: :utc_datetime)` precision, so no silent microsecond
  mismatch between what's written and what a reload returns.
- `updated_at` is left alone — only `inserted_at` is overridden, so it still
  answers "when was this row actually written," which is the property the
  moduledoc promises.

### BUG - MEDIUM: shipped with zero test coverage — FIXED

Nothing in `test/` exercised `create_comment/4` at all before this PR (the
only pre-existing integration suite, `reactions_test.exs`, covers
like/dislike). The PR's own description says it was "verified live in a host
app," which is real verification but not one that survives the next refactor
of `apply_backdate/2` or `Comment.changeset/3`.

**Fixed:** added `test/integration/backdated_comments_test.exs`, four cases
against a real database (via `PhoenixKitComments.DataCase`):

- a real `DateTime` overrides the autogenerated `inserted_at`, on both the
  return value and a fresh `Repo.get` reload — and `updated_at` stays close
  to "now," not the backdate;
- sub-second precision truncates to match the column;
- a non-`DateTime` value (a plain ISO8601 string, standing in for whatever a
  careless client-forwarding caller might send) is silently ignored rather
  than cast or raising;
- omitting `:inserted_at` entirely keeps the normal autogenerated timestamp.

All four pass against the real schema. `mix test`: 80 tests, 0 failures
(76 pre-existing + 4 new).

## Comment card rework — kebab menu, hover-revealed actions

Read the full `render_comment/1` template and the `handle_event` handlers for
`edit_comment` / `delete_comment` / `reply_to`.

- **Server-side authorization is untouched by this PR.** `do_save_edit/3`,
  `save_edit_for/4`, and `do_delete_comment/2` all still gate on
  `can_edit_comment?/2` / `can_delete_comment?/2` independently of what the
  client rendered — the dropdown's `:if={can_edit_comment?(...)}` guards are
  a UI convenience, not the authorization boundary. A user who forges the
  `phx-click` payload still hits the same server-side check that existed
  before this PR.
- **Kebab self-blur is correctly ordered.** The inline
  `onclick="document.activeElement && document.activeElement.blur()"` runs
  at the click target during the browser's target phase, before the event
  bubbles to LiveView's delegated listener — so the blur (which closes the
  daisyUI focus-driven dropdown) happens without ever suppressing the
  `phx-click` that follows it. Verified this is standard DOM event ordering,
  not a race.
- **`group/comment` named-group scoping is consistent.** The outer card div
  declares `group/comment`; both the kebab wrapper and the new Reply button
  reference it by name (`group-hover/comment:opacity-100`), so they don't
  collide with the pre-existing unnamed `group` used by the decoration-label
  pencil icon in the same template.
- **`reply_to` already validates the comment belongs to the current thread**
  (pre-existing check, unmodified) — moving the button's position and
  visibility didn't touch that logic.

### OBSERVATION: hover-reveal hides actions by default on touch devices

Edit/Delete (behind the kebab) and Reply are now `opacity-0` until
`:hover`/`:focus-within`/`:focus-visible`. Touch devices don't match `:hover`,
so on a phone these controls are present and tappable but invisible until the
user already knows where to tap. This is consistent with the pre-existing
decoration-pencil-icon pattern elsewhere in this same file
(`opacity-0 group-hover:opacity-60`), so it's project convention rather than
a regression introduced by this PR — noting it here rather than "fixing" a
design decision the PR's own author verified live and the pattern already
established elsewhere. Not blocking.

## What Was Done Well

- The `:inserted_at` backdate design is deliberately narrow: unreachable
  through `cast`, unreachable through the shipped form path, and safe even
  against a hypothetical careless host because only a real `DateTime` struct
  can trigger it.
- The kebab-close race (dropdown staying open over a deleted/edited card)
  was correctly diagnosed as a focus-vs-LiveView-patch problem and fixed with
  the right mechanism (blur on the actual click target, ordered before
  bubbling) rather than a `phx-click-away` bolt-on.
- IDOR / permission checks for edit and delete were left exactly where they
  already were — the PR didn't move authorization logic into the template
  along with the UI.
